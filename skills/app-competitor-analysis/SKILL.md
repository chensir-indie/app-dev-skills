# App Competitor Analysis

Explain how a competitor works, why its experience takes that shape, and what the user's product could adopt. Follow the requested decision and evidence scope.

## 1. Choose the scope

Identify the user's product/task, target competitors, requested dimensions and available evidence. Begin from a usable brief; ask only for missing information that changes the work. Use the user's language and keep domain-specific preferences in the project report. Read [research-methods.md](references/research-methods.md) to turn the brief into a decision, falsifiable question, comparable task subgroup and selected methods. Use its completion criteria, not a universal list of report dimensions.

- **Single app:** trace its primary task end to end and relate UI and implementation to it.
- **Full landscape:** inventory the entire requested set and deliver a separate report for every product. Group by user job and mechanism; deeper sampling still preserves individual reports.
- **Limited evidence:** when scope or access restricts acquisition, analyze what available artifacts establish and record the boundary. Sparse starting material alone calls for acquisition, not a gap-only conclusion.

## 2. Establish evidence

Read [evidence-model.md](references/evidence-model.md) before forming conclusions. Pin product/platform identity, version, source date and account/device/state context. Inspect the underlying artifact for material claims; refresh time-sensitive claims through official sources when current behavior is requested.

Prefer supplied material and authorized local artifacts. Use available browser, native UI, image and artifact tools according to their instructions. Missing device access limits runtime conclusions; screenshot and static analysis can continue. Follow existing authorization for acquisition and keep private or third-party artifacts out of the shareable skill package.

When consequential evidence is missing, read [evidence-acquisition.md](references/evidence-acquisition.md) and execute its loop: diagnose → define closure proof → prioritize → acquire and inspect → reconcile → update the report/maps → recheck. Distinguish unattempted, partially answered and concretely blocked questions. Text extraction cannot close a pixel/runtime question. Record real attempts and change acquisition routes when useful; a queue of future work does not replace currently possible authorized research. Do not purchase, bypass protections or upload private data merely to fill a report.

Research needs no Python. Before running a bundled renderer or audit, run `sh scripts/doctor.sh` from this skill directory. It selects Python 3.9+ from `python3` or `python`; use the reported command. If it fails, follow [environment setup and fallback](README.md#run-the-helpers), continue independent research and keep script-dependent work pending. The check installs nothing.

Before detailed analysis, record which selected methods are completed, partial or not run and what each can establish. Use [research-workbook.md](assets/research-workbook.md) for filled capability, task, issue, decision and experiment records. Public-material review can produce a substantive teardown; participant studies, runtime comparisons and cohort measurements require their own actual data. Keep unknown measures null and retain a concrete acquisition route.

## 3. Analyze only the needed dimensions

Read [analysis-depth.md](references/analysis-depth.md) before detailed analysis or repairing a shallow report. First recover the competitor's capabilities, visible organization and concrete task records; challenge the proposed product model with contrary pixels, entry points and source details. Technical labels such as “AI” do not establish separate workspaces. Explain what the competitor does and how it works before proposing changes to the user's product. Preserve useful atomic capabilities, control states and known steps; additional caveats or test plans do not replace that explanation.

Load references for requested dimensions with useful evidence. Mark an unrequested dimension briefly as `out_of_scope`; requested but unsupported dimensions retain a specific gap and next observation. Sparse evidence can still support conditional reasoning: explain the established constraint, candidate mechanisms and how the unresolved difference affects the decision.

| Dimension | Read when needed | Analytical result |
| --- | --- | --- |
| UI and information architecture | [ui-analysis.md](references/ui-analysis.md), then [design-specification.md](references/design-specification.md) for a detailed pass | Inspect the full visible element inventory; explain the design system and export a source-linked Design.md per product |
| Interaction and product logic | [interaction-analysis.md](references/interaction-analysis.md) | Map tasks and states; show the UX review of entry, choices, feedback, recovery and durable completion with counterexplanations and validation |
| Technology and data | [technical-analysis.md](references/technical-analysis.md) | Trace input → trigger → transform → output → storage → consumer; bind static claims to the artifact and call path |

Separate app UI from promotional framing. Static pixels do not establish unseen behavior or a technology stack. For uncertain mechanisms, retain alternatives and a distinguishing observation. Record paywalls, permissions, accounts, offline behavior and repeat-use constraints when they affect the main task; separate declared access from observed use.

## 4. Synthesize product decisions

Read [synthesis-and-report.md](references/synthesis-and-report.md) and apply the depth review in [analysis-depth.md](references/analysis-depth.md#review-depth-before-delivery). Compare mechanisms against the same user job and constraints while preserving the complete inventory. Connect adopt/adapt/defer recommendations to evidence, the user's situation, a tradeoff and a small validation task whose possible outcomes change the decision. Preserve user decisions unless new evidence warrants explaining a change. Apply the research method's decision and experiment records to consequential findings, including alternative explanations and a result that reverses the recommendation. Use optional scoring only with predeclared anchors, common evidence coverage, hard gates and sensitivity; otherwise compare mechanisms without inventing a numeric winner.

## 5. Deliver and verify

Read [html-delivery.md](references/html-delivery.md) for the schema, original example, renderer and browser checks, and apply [report-design.md](references/report-design.md) for the visual product-study layout, concrete reference comparison, shared tokens and diagram composition. Use [apple-web-design.md](references/apple-web-design.md) as its usability baseline; preserve an explicit user direction. For visual delivery or weak presentation, use [design-quality-review.md](references/design-quality-review.md): choose one design system, inspect the argument and layout, repair the shared cause, then record actual rendered checks. It distinguishes the competitor's platform conventions from our web report and uses critique, typesetting, layout, hardening and polish as review lenses. These are not claims of native-interface certification. Use [report-template.md](assets/report-template.md) as an authoring outline.

By default deliver **one complete HTML report per competitor**, plus a searchable `index.html` for multiple products. At large desktop widths, keep the product library beside a content workspace with separate URL-addressable views for overview, capabilities, interface, interaction, technology, decisions and sources. Preserve native deep links, view-aware history and continuous reading; use a product chooser and compact view navigation on phones. Give the collection a searchable left product list with native report links, current-product indication and an accessible phone switcher; keep local chapters distinct from product navigation. Deliver the default reading copy as a portable folder with shared local assets; export a single-file standalone copy when requested. Keep the `assets` folder beside the HTML files and verify the reader's actual preview route. Open with the product's identity, its defining experience and a finding tested against the inspected material. Give explanatory imagery a prominent, readable place; identify promotional framing and uncertain versions. Provide four evidence-linked visual maps: feature hierarchy, directed task flow, screen relationships and technical data flow. Distinguish real UI organization from analytical grouping. Preserve acquired steps, branches and loops; show missing route evidence as a break rather than bridging it with a generic lifecycle. Readers must be able to find and compare the maps without reading every chapter first. Honor an explicit request for another format; keep narrow analyses proportionate.

For detailed UI work, also export `design/<product-id>/Design.md` using [the design specification contract](references/design-specification.md). Author its element inventory, rules, components and UX records before rendering; link the document in the interface view and show task-specific UX findings in the interaction view. Update the canonical Skill and generator first, then reapply to every requested report. Keep research metadata out of the main reading layer while retaining consequential evidence qualifiers.

For report interaction work, apply [reader-interactions.md](references/reader-interactions.md). Keep product/view/history state coherent, inspect nodes and evidence without losing the argument, offer a formatted Design.md reader, and preserve native offline links. Verify complete reading journeys and interrupted/failed report switches on the regenerated collection.

Each report covers identity and conclusion, inspected UI evidence, core task/states, technical mechanisms, operating conditions, strengths/costs, product decisions, gaps and traceable sources. Use an authored reading layer: a short product headline and purpose, a distinct finding, useful imagery, then mechanisms and decisions. Apply the [editorial reading review](references/design-quality-review.md#edit-the-reading-copy) before rendering; `brief` and section `summary_blocks` keep concise reading separate from complete supporting analysis. For diagrams or weak visual explanation, apply [diagram design](references/diagram-design.md): author task-scoped capability tiers, a spine that follows actual transitions, and technical responsibility roles with a concrete evidence boundary; place each complete map with its explanation. State a finding fully where it belongs and link back instead of repeating it across chapters. Summarize consequential gaps near the affected finding; place long acquisition histories, source metadata and exhaustive tables in clearly labeled disclosures or appendices. Do not hide a qualification that changes the conclusion. Expand all useful available evidence before declaring a chapter unsupported.

Keep the product's primary task separate from this report's most interesting finding. Classify by the supported primary job, retain secondary capabilities without letting an optional feature define the whole app, and keep platform/version scope consistent across index, opening and maps. A technically interesting save pipeline is not itself market positioning. Use the optional `positioning` record for a source-linked task summary; label it as research synthesis rather than proven audience or market fit.

When presentation is rejected or a visual reference comparison is requested, follow report-design.md to deliver actual reference/old/new captures together in a project-local HTML comparison; repair opening geometry, evidence proportion, hierarchy and diagram meaning before applying the design to the complete set. Before generating the full set, review a representative report's main claim against its strongest counterexample, then apply the rendered composition checks in report-design.md to sparse, image-based and dense content. Implement the shared typography, neutral surfaces, grouping and controls in reusable styles and components. Keep product-specific imagery and conclusions in the report project; a palette change alone does not fix repeated text, tiny screenshots or large tables.

Include an acquisition receipt: consequential gaps, actual routes/results, evidence added to diagrams and chapters, remaining questions and next actions or concrete resumption conditions. For a broad study, validate the record with `python3 scripts/audit_acquisition.py path/to/acquisition.json` (or the interpreter reported by doctor). A valid ledger is not completed research; unresolved in-scope questions remain visible.

Open the actual generated HTML in a browser using an allowed route. Apply the [design completion checks](references/apple-web-design.md#completion-checks), including desktop/phone layouts, enlarged text, keyboard use, reduced motion and print; revise defects before checking the rest of the set. Check inventory and chapter coverage, graph breadth and connectors, node details and sources, diagram switching, images, navigation and index search/filter. If browser access is unavailable or denied, keep the concrete visual and interaction checks pending without bypassing that restriction. Rendering success, a screenshot's existence and passing structural tests alone do not satisfy delivery review.

For inaccurate navigation or slow output, follow [navigation and performance checks](references/html-delivery.md#navigation-and-performance): reproduce the failing action, measure the actual final files, repair the shared cause and compare the same operation before/after. Test cold deep links, rapid chapter changes, source/back restoration and node cleanup. Reserve image geometry and use bounded reading previews; retain exact original evidence. An overflow-free layout is not a performance test, and a fast warm desktop sample does not establish smooth behavior on every device.

For actual task-study records using first-valid-attempt analysis, run `scripts/study_metrics.py study.json --output summary.json`; see the [synthetic schema example](assets/study-record.example.json). Review raw recordings and comparison conditions separately: arithmetic checks cannot certify research validity.

For a structured ledger run the optional audit described in [evidence-model.md](references/evidence-model.md); a readable evidence table is sufficient for small work. Before delivery apply [evaluation.md](references/evaluation.md), including change-app-name, decision and cross-section checks on actual findings. Automated coverage or repetition checks only direct review; they do not certify analytical depth. Return clickable report links and preferably a rendered diagram preview. State evidence completeness separately from HTML delivery completeness, device validation, implementation and release.

When continuing into design or implementation, reference the reports and evidence instead of repeating them. Carry the user's chosen decisions, unresolved hypotheses and requested next artifact; recommendations alone do not establish an approved design or a real capture of the user's app.
