# 工作流与交接

[English](workflows.md) · [文档导航](README.zh-CN.md) · [选择技能](../README.zh-CN.md#选择技能)

按用户手头的材料和要求的终点选择。推荐、执行或排除某个分支前，读取对应 `SKILL.md`；名称和摘要只用于导航。沿用已有授权，保留项目中可用的文件。

## 选择交付终点

| 用户需求 | 入口与第一步 | 完成信号 |
| --- | --- | --- |
| 解释竞品或定位产品差距 | [App Competitor Analysis](../skills/app-competitor-analysis/SKILL.md)：盘点证据，并尝试补齐缺失材料 | 每个竞品的 HTML、所需关系图/索引、可追溯结论、明确未知项、审计结果和产品建议 |
| 探索设计方向或编写图片提示词 | [Image to Layered HTML Prototype](../skills/image-to-layered-html-prototype/SKILL.md)：进入概念/提示词分支 | 所需方向或提示词、约束和选择依据。仅在要求图片时生成图片；HTML 是另一个终点 |
| 还原已认可图片 | [Image to Layered HTML Prototype](../skills/image-to-layered-html-prototype/SKILL.md)：冻结参考身份，建立页面/状态合同 | 可编辑页面与素材、manifest、浏览器截图、要求的对比和真实剩余差距 |
| 修复现有分层页面 | 同一技能：先盘点当前 HTML 和素材，再界定修复范围 | 对照保留的参考和合同验证修改区域/状态，保留未受影响的结构 |
| 适配现有 iOS App 的可调整尺寸布局 | [iPhone Duo Adaptation](../skills/iphone-duo-adaptation/SKILL.md)：识别界面框架，以原应用为依据分析整体布局并提出最小必要改动 | 整体布局分析 → 映射 Apple HIG 的适配意见 → 覆盖具名 Duo 形态、同状态对比和真实浏览器证据的完整 HTML 原型；仅明确只要审计/意见时提前结束 |
| 制作或调整商店封面 | [App Store Cover Generator](../skills/app-store-cover-generator/SKILL.md)：区分新建项目与现有矩阵，先检查源码和配置 | 从可编辑源码导出要求的矩阵单元，记录布局/本地化检查，并对照最终哈希完成视觉审查 |
| 打包、上传 TestFlight 或交付商店资料改动 | [App Publish Skill](../skills/app-publish-skill/SKILL.md)：发现应用发布合同，冻结用户要求的终点 | 仅交付对应阶段证据：本地签名产物、精确上传回执、允许清单内的商店资料交付，或另行授权的验收／提审／公开状态 |

有限证据可以支持注明范围的报告或概念；缺少截图、测量或审查的部分仍待完成。明确说明完成的是哪个分支，以及它的限制。

## 应用发布

App Publish Skill 按目标平台和实际框架编排现有 App 发布：原生 iOS、Flutter、具有受支持本地 native 工程的 React Native/Expo，或原生 Android。通用源码／基线／制品／资料阶段与框架本地构建适配分开。首次使用或缺少运行时时先按技能安装指南处理，再验证 Ruby/Bundler、项目 gems 与实际 Fastlane 版本。先发现项目真实 lane、包装脚本、发布合同和已有授权，再选择命令；不同仓库的 lane 名称与版本输入并不相同。只打包的需求止于已核验的本地制品。明确授权的 TestFlight 上传使用本机构建签名和项目自有 Fastlane/Spaceship，对精确 IPA／版本／build 收到 Apple 成功回执即停止。源码 commit、产物哈希与平台回执一起保留。处理、有效状态、测试组分配和精确构建安装属于后续状态；列表延迟不能触发再次上传。

已授权的商店资料工作可以独立于二进制上传。冻结文字字段与截图文件的允许清单，保留受保护的法律／订阅值，检查全部已启用语言区域 × 设备 × 页面矩阵，交付后重新读取受影响的远端状态。只改商店资料时复用已验收源码与产物证据，无须重建。仅制作封面进入 App Store Cover Generator；需要上传时，将精确导出、哈希与审查记录带入发布阶段。

后续精确构建验收、提交审核和手动公开发布分别需要对应请求范围与证据。提审前确认发布方式及公开后果；审核通过不等于公开可见。可选 Android 路径在本地构建签名，通过已认证 Chrome Play Console 操作已授权轨道；使用自身版本、产物和轨道检查，不套用 TestFlight 命令或回执含义。安装技能、运行 doctor 或生成离线候选提案均不操作 App／商店，也不构成发布授权。

## iOS 主流框架可调整尺寸适配

整体布局盘点后，将官方依据中的全部规则、规范与建议格式化为目标工作区的 JSON/Markdown 账本。首次创建或修改原型实现前，逐条填好适用性、决策、计划落地路径、排除／原生后置理由和已采纳的项目约定，再冻结账本、原设计参考、页面／形态覆盖和迁移设计交接的哈希与时间。验证可以待执行，空白 pending 账本通过结构检查不代表满足交接；已有晚补记录保留真实时间线。设计规范、意见、HTML 与验收沿用同一组 ID，并在项目 Agent 指令增加条件指针。其他框架专用规则以已识别框架为理由标为不适用。宣称默认交付完成前补齐实际证据并通过完成检查。

通用指导和集合工作流与具体应用的 `project_conventions` 分开，注明项目依据和对应通用 ID；完成检查覆盖两者。IMX 示例是按条件采纳的项目输入，不作为其他应用的默认义务。

Duo 的目标是协助现有应用完成 iPhone Duo 适配优化；分析、建议与完整 HTML 原型用于使必要改进可评审、可验证。默认先识别界面是 SwiftUI、UIKit、Flutter、React Native 还是 WKWebView 壳，再按**整体布局分析 → 适配意见 → 完整 HTML 原型**推进。盘点页面、共享组件、导航、浮层和重要状态，以原应用的视觉、组件、令牌、文案与可用页面结构为主要设计依据；记录保留／适配／变更及最小必要改动的理由。现有单栏或页面栈可用时保留，多栏、新导航、图标、文案和功能不是迁移默认要求。按当前 Apple iPhone HIG 和 Duo 指导给出意见，分别标明现状证据、官方指导、框架契约和产品选择。只有明确只要审计或意见才提前结束；详见技能入口及[迁移评审合同](../skills/iphone-duo-adaptation/references/migration-review.md)。

按[设备展示合同](../skills/iphone-duo-adaptation/references/device-presentation.md)采集实际外观与显示尺寸，分清截图像素、逻辑点和预览缩放；Closed／PartiallyOpen／Open 与旋转分别控制。主体突出活动设备与应用，诊断默认折叠，外框视觉、原应用设计与交互分别验收。

HTML 阶段按 [BUILD WEB APPS 交接合同](../skills/iphone-duo-adaptation/references/build-web-apps.md)优先构建。先发现、读取实际合同，记录身份及安装／上游源码执行方式：保留原设计的迁移或局部修复使用 `frontend-testing-debugging` 优化流程；需要且已授权新视觉界面时才选择 `frontend-app-builder`。选择新建流程时遵守其实际 Image Gen 条件，完整迁移不自动满足小改动例外；生成概念不能替代原设计依据。传入已冻结的现状、意见、设计、覆盖矩阵、迁移记录和通用／项目规则，保留本地可编辑源码及可运行产物。不可用时明确替代流程；托管单独按请求范围处理。Duo Skill 和生成规则正文使用英文。

原型通过应用画布外的可用评审控件，明确展示适用的外屏横竖、内屏横竖、应用在左／右的分屏，以及书本／桌面／站立等半折叠环境，记录不适用或待验证的理由。切换同一运行实例并保留路由、选择、草稿和阅读锚点；对比原应用与适配后同页同状态。键盘、大字和浮层是独立压力状态。用实际浏览器验证控件确实改变可用布局、动作可达和状态连续性，保存截图、尺寸及结果；只有形态标签变化不算通过。未经验证的尺寸与区域标为评审假设，不虚构官方屏幕、铰链或相机几何；未做浏览器检查时 HTML 验收保持待完成。布局分析和 HTML 制作无需 Xcode、模拟器、真机或该框架工具链，原型证据不能证明原生 Duo 行为。

产品实现与设备验证是后续另行请求的阶段，不能替代 HTML 交付。收到此类请求后，在产品仓库使用已识别框架自己的运行方式，记录实际命令、目标/构建模式与证据。新增 Flutter 页面须有经生产导航进入的集成测试；SwiftUI、UIKit、React Native 和 WebView 壳使用各自合同，不套用这道 Flutter 门槛。设备敏感生产改动须跑该框架的生产模式冒烟测试，iOS 硬件行为存在差异时还须真机验证。缺少的原生检查保持待完成，审计、原型或 doctor 结果不能证明原生适配验收。

## 阶段之间传递什么

在现有报告或项目中保留简短交接记录。引用文件，避免整份复制内容：

```text
下一步要求的结果：
产物路径与身份/哈希（文件已冻结时）：
来源、版本/日期、视口和交互状态（适用时）：
观察事实 / 来源声明 / 推断 / 未知：
已完成检查与证据文件：
剩余差距与下一项具体动作：
```

已有 schema 与状态字段仍是权威定义。交接记录用于定位证据，不新增审批步骤，也不替代 manifest。

| 阶段转换 | 带入下阶段 | 进入条件 |
| --- | --- | --- |
| 竞品分析 → 设计方向 | 报告、证据链接、产品约束、优先机会及未知项 | 在用户范围内选定设计问题；竞品推断继续标为推断 |
| 设计方向 → 分层还原 | 选定参考及哈希、页面/状态、尺寸、素材/字体和验收标准 | 只要提示词时到此结束；完整还原中缺参考或素材时保留约束 |
| 分层原型 → App 实现 | 可编辑源码、设计合同、对比结果和已知差距 | 在产品仓库实现并做设备验证；原型通过不能证明这些步骤已完成 |
| 适配原型 → 产品实现 | 全 App 布局清单、官方规范适配建议、完整 HTML 源码、浏览器证据、布局/状态决策与原生验证矩阵 | 用户另行请求实现后进入；完成相关产品检查，并明确待补的设备证据 |
| 已实现 App → 商店封面 | 实际 App 截图、已知的 App/构建身份、有证据的卖点、语言/设备/页面计划 | 标注示例/概念素材；产品声明及基于截图的交付使用真实产品证据 |
| 封面导出 → 商店流程 | 精确 PNG、矩阵、哈希、联系表和审查记录 | 上传/提交属于另行授权的任务并须核对平台状态；导出保持为导出状态 |
| 已核验本地制品 → TestFlight 上传 | 冻结意图、实时商店基线、已同步源码 commit、产物身份／哈希与项目检查结果 | 明确 TestFlight 范围并使用项目自有 Fastlane；精确产物的成功回执即结束上传任务 |
| 上传回执 → 后续商店阶段 | 精确 bundle／版本／build、源码 commit、产物哈希、回执与另行审查的商店资料 | 按要求授权验收、元信息／截图、提审或公开发布；核验对应状态，不重复上传 |

已有项目从当前阶段进入，不能为了走完整流程而从模板重建。

## 缺少能力时

在即将执行依赖脚本之前运行该技能对应范围的 `doctor.sh`。概念或阅读任务无须先装齐全部渲染环境，安装与修复见[环境支持](runtime.zh-CN.md)。

继续独立工作，依赖失败工具的步骤保持待完成。说明缺少的运行时/包/浏览器、修复命令和重跑检查。替代工具须能提供所选合同要求的证据，不能把缺失检查写成假定通过。
